O que existe hoje no Pelada Pro, e o quanto se afasta do que os docs 01–08 pedem

Auditoria do backend Node.js, do painel web (gestor/jogador) e do app mobile Expo, cruzada com a especificação oficial. Cada achado abaixo tem o arquivo e a linha de onde veio.

3 plataformas auditadas ~60 telas mapeadas 23 tabelas confirmadas no Supabase 0 políticas de RLS em todo o banco 9 achados críticos de segurança Corte lógico: 09/09/2026

00Sumário executivo

Antes do detalhe: o sistema funciona, mas em três camadas com modelos de dados e regras diferentes entre si — não um único "Pelada Pro", e sim três implementações parcialmente sobrepostas.

17
telas do app mobile existem no código mas não estão conectadas a nenhuma rota — dados 100% mockados
3
implementações diferentes do sorteio de times (backend, web, mobile) — nenhuma aplica a regra de memória de duplas exatamente como especificado
5
tabelas em UUID, órfãs e sem nenhuma política de RLS — travadas para qualquer acesso via chave anônima/autenticada
0
telas com login social (Google/Apple) realmente funcionais, em qualquer plataforma
Achado que muda o diagnóstico: o "caminho paralelo Supabase" que os documentos apontam como causa da re-sincronização de times na web é código morto — window.supabase nunca é carregado no navegador. A causa mais provável é cache em memória do backend Node (por processo) ou uma segunda aba com a tela de Partidas aberta reenviando o placar. Ver seção 04.

02Banco de dados

Um único Postgres hospedado no Supabase (projeto xgsdaavryzhqxkwsonkk), acessado por SQL cru no backend. backend/database.sql é só o esqueleto original de julho — o schema real cresceu por scripts avulsos e, em boa parte, direto no Supabase Studio, sem deixar rastro no repositório.

Atualização · 06/09/2026, sessão seguinte: conectamos direto no Postgres do Supabase (sem pg_dump disponível localmente, usamos uma consulta equivalente via information_schema/pg_catalog com o pacote pg já presente no backend — script somente leitura em backend/scratch/schema_audit.js) e confirmamos: 23 tabelas reais no schema public. Isso fecha a pendência 1 do relatório original e revela algo mais preciso do que a hipótese anterior — ver o quadro abaixo.
Confirmado: existem duas modelagens de dados coexistindo no mesmo banco. 18 tabelas usam id inteiro/serial (o schema "legado" que o backend Node realmente lê e escreve, com dados de verdade). Outras 5 tabelas usam id UUID — usuario_grupo, configuracao_pelada, jogador_time, desempenho_goleiro, gols — formando um fragmento de schema paralelo, sem nenhuma FK ligando-o ao resto do banco (tipos incompatíveis: UUID vs. integer). Nenhum controller do backend escreve nessas 5 tabelas. É provavelmente o início de uma migração para o padrão UUID do Supabase Auth (coerente com a decisão do doc 08 de ir para Supabase Auth) que foi abandonada antes de ser conectada a qualquer código. Ver detalhe logo abaixo.
Os nomes que o mobile consulta (profiles, grupo_membros, pelada_presencas, quadras, jogadores, sorteios, ranking_grupos, conquistas) não existem em NENHUMA das 23 tabelas reais. Toda consulta do app mobile a essas tabelas retorna erro "relation does not exist" em produção — o mobile foi escrito contra um schema que nunca chegou a ser criado no banco.

Correção do relatório anterior"notificacoes" e "mvp_partida" não existem de fato

A primeira leitura (só de código) listou essas duas como "usadas mas sem script de criação". Com acesso direto ao banco, confirmamos que nenhuma das duas existe nas 23 tabelas reais. Os INSERT INTO notificacoes (convocacaoController.js:422-425) e UPDATE mvp_partida (usuarioController.js:525) falham em produção — e, dado o padrão de catch silencioso já visto em todo o backend, o erro provavelmente é engolido sem log. Ou seja: notificações in-app e o recurso de "MVP da partida" não funcionam, silenciosamente, hoje.

Só que está isolada: tipo de chave incompatível com usuarios.id/grupos.id (integer), sem FK, sem nenhuma rota de API que a leia ou escreva, e com RLS ligado sem nenhuma política — nenhum papel (nem anon, nem authenticated) consegue ler ou escrever nela hoje. Como as 5 linhas foram inseridas ainda não está claro a partir do código (nenhum controller ou tela toca essa tabela); provavelmente foi um teste manual direto no Supabase Studio durante uma exploração de arquitetura anterior.

Pergunta 4 da tarefaPolíticas de RLS existentes hoje

Resposta direta: nenhuma. A consulta a pg_policies devolveu uma lista vazia — 0 políticas de RLS em todo o banco, em qualquer tabela. A situação real de RLS é:

  • 18 tabelas com RLS totalmente desligado — incluindo usuarios, grupos, peladas, convocacoes e transacoes, ou seja, todas as tabelas com dados pessoais e financeiros reais.
  • 5 tabelas com RLS ligado mas zero políticas — na prática, isso bloqueia qualquer leitura/escrita por chaves anon/authenticated (só o papel dono/serviço, que é o que o backend usa via conexão direta ao Postgres, consegue acessá-las). É o fragmento UUID acima.
Isto é mais grave do que "RLS incompleto" (SEG-001 do doc 06). O app mobile carrega a anon key do Supabase diretamente no código-fonte (src/lib/supabase.ts) e usa o cliente Supabase para ler/escrever tabelas como usuarios (tela app/premium.tsx) e outras do schema legado — todas com RLS desligado. Com RLS desligado, a API REST automática do Supabase (PostgREST) concede acesso conforme os grants padrão de anon/authenticated, sem depender do JWT próprio nem das checagens de papel do backend Node. Na prática, isso significa que qualquer pessoa com a anon key (já exposta no bundle do app) pode, em tese, consultar/alterar essas tabelas direto pela API do Supabase, contornando completamente a autenticação e as regras de autorização do backend. Recomendamos não testar isso ativamente em produção sem uma janela controlada — mas o achado por si só (RLS desligado + chave anônima pública) já justifica tratar como crítico e confirmar/corrigir antes do corte de 09/09.

03Regras de negócio no código

Crítico do produtoSorteio de times — três implementações divergentes

Não existe "o" algoritmo de sorteio: há três, um por plataforma, em estágios diferentes de fidelidade à regra de memória de duplas.

OndeComo funcionaMemória de duplas
backend/sorteador.js20 simulações "snake draft" ponderadas por estrelas, escolhe a de menor scoreMorta — formacaoController.sortear nunca passa o histórico; o parâmetro sempre chega vazio
components/modals/sorteio.js (web)20 candidatos Monte Carlo + refinamento local por trocas (meta: diferença de média ≤0,5)Parcial — penalidade suave no score, histórico acumulado para sempre em localStorage, sem janela deslizante
src/utils/sorteioComMemoria.js (mobile)Distribuição guiada 2-2-1-1 + mecanismo de "sacrifício" de duplas repetidasA mais fiel — mas só é usada na única tela mobile de sorteio real

Nenhuma das três implementa como restrição rígida a regra "diferença ≤2 estrelas, tolerância 3" nem o piso combinatório de 8 duplas repetidas citado no doc 01/06 — são heurísticas que tendem para o equilíbrio, sem garantia matemática.

PresençaFila de espera e promoção

O backend tem dois caminhos que liberam vaga, com comportamentos inconsistentes entre si:

  • Remoção pelo gestor (convocacaoController.desconvocarPorGestor) promove o primeiro da fila automaticamente sem checar saldo nem cobrar — risco de o atleta entrar "de graça".
  • Autorremoção do atleta (convocacaoController.remover) não promove ninguém: só envia push avisando que uma vaga abriu, e o próprio atleta precisa confirmar/pagar.

Nenhum dos dois caminhos implementa exatamente a regra do doc 03/05 ("promove automaticamente se tiver saldo ≥ valor da pelada, senão notifica para pagar"). No mobile, a fila é 100% mockada (não há lógica real).

FinanceiroLedger, saldo paralelo e correção destrutiva

O extrato (transacoes) e o saldo corrente (usuarios.saldo) são duas fontes de verdade mantidas manualmente, sem rotina de reconciliação. Mais grave: existem dois padrões de correção coexistindo —

  • Correção destrutiva (a maioria): editar_transacao.js → UPDATE/DELETE físico da linha original, sem trilha. Viola a regra "nenhum lançamento apagado silenciosamente" (doc 01, item 6.4 / FIN-010).
  • Estorno auditável (só para presença/Pix): estornarSaldoAtleta cria uma nova transação de devolução, preservando a original — o padrão certo, mas aplicado de forma inconsistente.

O dashboard web calcula "Caixa Real", "Saldo dos Atletas" e status de pagamento parcial lendo tags de texto embutidas na descrição ([PAGO:x/y], [PENDENTE]) em vez de colunas estruturadas — funciona, mas é frágil a qualquer mudança de texto futura.

ConfidencialidadeJogador vê o financeiro de todo o grupo

A regra "jogador só vê a própria situação" (doc 05, seção 3.5) está violada hoje: pages/jogador/financeiro.js carrega o mesmo dashboard agregado do gestor (caixa total, saldo de todos os atletas, todas as vaquinhas) e só esconde botões de ação via uma checagem (Auth.getUserRole) que nem existe em auth.js — funciona por acaso, caindo num fallback baseado na URL.

VaquinhaCampanhas de arrecadação

Fluxo completo: criar campanha (título, meta, valor sugerido, categoria — sem campo de prazo/data-limite, ao contrário do que o doc 02 supõe) → contribuir por saldo interno (instantâneo) ou Pix real via Mercado Pago com polling a cada 2,5s. Um botão "Simular Aprovação" fica sempre visível no modal de contribuição, sem nenhuma trava de ambiente — um atalho de teste exposto em produção. Não há limite contra ultrapassar a meta, e contribuições não se vinculam a uma pelada específica, só ao grupo.

PapéisTesoureiro não existe

O modelo de três papéis por grupo (organizador/tesoureiro/jogador) do doc 05 não existe no código. A única distinção real é usuarios.tipo, com valores jogador, gestor, ambos, convidado, incorporado — nenhum deles é "tesoureiro", e nenhum é por grupo (é global ao usuário).

Card PremiumPersistência certa, tela quebrada

A correção do bug do iPhone está implementada em app/premium.tsx: memória → AsyncStorage (com try/catch) → Supabase como fonte da verdade, com um listener de AppState comentado explicitamente como "crítico para iPhone". O problema é outro: a tela usa três variáveis nunca declaradas (isLucasGuerreiro, PlayerCard, userStats) e crasha antes de renderizar — a arquitetura certa existe, mas é inacessível.

AutenticaçãoLogin social — inexistente nas duas plataformas

Na web, "Entrar com Google" (components/modals/google_auth.js) não é OAuth real: pede para o usuário digitar manualmente um e-mail e usa uma senha mock fixa ("google_oauth_secure_password") — além disso, esse modal está órfão, nenhum botão o chama. No mobile, não há nenhum vestígio de Google/Apple. Em nenhuma das duas plataformas o login social funciona hoje.

Regra não documentadaBônus: a "regra das 2 horas"

O backend implementa uma regra financeira real e ausente dos documentos 01–08: convocacaoService.verificarRegra2Horas bloqueia reembolso para cancelamentos feitos a menos de 2h do início da pelada (comparando fusos de Manaus e Brasília, dando benefício da dúvida ao atleta). Vale registrar essa regra no doc de fluxos antes de reconstruir.

Pendências que precisam da sua decisão

Nada foi alterado. Estes são os pontos que travam o avanço para a próxima fase (arquitetura/schema novo) até você decidir.

Duas pendências da primeira rodada já foram resolvidas nesta consulta direta ao banco: o schema real (23 tabelas, com colunas e chaves) e as políticas de RLS (zero em todo o banco) — ver seção 02. As pendências abaixo substituem as originais 1 e 5, agora mais específicas.
  1. Decidir o que fazer com o fragmento de schema em UUID (usuario_grupo, configuracao_pelada, jogador_time, desempenho_goleiro, gols).Está desconectado do restante do banco (tipos incompatíveis, sem FK, sem controller que o use) e travado por RLS sem políticas. É provavelmente o começo de uma migração para UUID/Supabase Auth abandonada. Aproveitar como base do schema novo, ou descartar e desenhar do zero?
  2. Habilitar RLS com políticas reais antes do corte de 09/09.Hoje 18 tabelas com dados pessoais e financeiros (usuarios, transacoes, peladas, convocacoes, grupos) têm RLS desligado, e a chave anônima do Supabase já está exposta no app mobile. Isso é um risco ativo em produção, não só uma lacuna do sistema a reconstruir.
  3. Investigar se as tabelas que o mobile consulta (profiles, grupo_membros, pelada_presencas, quadras, jogadores, sorteios, ranking_grupos, conquistas) já falharam silenciosamente em produção.Confirmado: nenhuma dessas tabelas existe nas 23 reais. Toda tela mobile que as usa (ex.: useGrupos.ts, services/api.ts) provavelmente já recebe erro "relation does not exist" hoje — vale checar logs/Sentry do app para medir o impacto real em usuários.
  4. Decidir o destino das ~17 telas mortas do mobile.Há trabalho de UI considerável (Financeiro, Ranking, Ao Vivo, Pós-Jogo) feito mas nunca conectado ao roteador real. Religar essas telas ou reescrevê-las do zero no novo sistema?
  5. Priorizar as vulnerabilidades de segurança ativas no sistema atual.O doc 08 prevê que o app antigo "permanece no ar" até o corte — mas o OTP exposto, o CORS aberto, a senha do banco em texto puro e o RLS desligado são riscos ativos em produção hoje, não só no sistema a reconstruir.
  6. Decidir se o Card Premium quebrado é corrigido ainda no legado ou só no novo sistema.A arquitetura de persistência já está certa; falta só religar três variáveis para a tela abrir — pode ser um reparo rápido e de baixo risco antes do corte.
  7. Confirmar se a exportação financeira em CSV/PDF (FIN-011) já existe em algum lugar não coberto por esta auditoria.Nenhum dos três agentes encontrou essa função no código investigado — precisa validar se é 100% a construir.
